# AgenTikZ MCP 接入方案

日期：2026-11-08
状态：已获用户批准，按阶段 A、B 实施。使用与验证说明见 `mcp-guide.zh-CN.md`。

## 1. 交付目标

同时补齐两条链路：

1. **Agent 使用外部 MCP**：用户在设置里添加文件系统、检索、文献管理等服务，启用后自动接入下一次 ACP 请求。
2. **Agent 使用 AgenTikZ 内置 MCP**：真实查询画布源码、AST、选区、布局诊断、组件库和主题，并通过工具提交可审核的画布修改。

首版以应用内 ACP Agent 使用为目标。面向其他桌面客户端的独立连接配置、公网访问和服务市场后续单独扩展。

## 2. 现有代码与需要补齐的部分

| 现有部分 | 现状 | 本次设计 |
| --- | --- | --- |
| `src-tauri/src/mcp/mod.rs` | 8 个工具的名称、描述和 schema | 增加实际 MCP 协议入口、参数校验和执行处理器 |
| `useAgentStore.mcpServerEnabled` | 内存占位，没有接入链路 | 迁移为持久化的内置服务开关 |
| ACP `session/new` | 只传工作目录，没有 MCP 服务配置 | 注入内置服务及已启用外部服务 |
| Workspace Store、Project Store | 当前画布和文件的事实来源 | MCP 复用现有解析、诊断、修改与撤销能力 |
| 聊天工具记录 | 既有 ACP 流，也有本地快捷操作生成的记录 | 区分真实 MCP 调用、原生 Agent 工具和本地快捷操作 |
| 修改提案 | 已有 Diff、应用和撤回；缺少完整目标/版本约束 | 文本提案与 MCP 提案统一增加目标画布和版本校验 |

## 3. 推荐架构

```mermaid
flowchart LR
    Settings[设置：内置开关与外部服务列表] --> ACP[应用 ACP 客户端]
    ACP -->|session/new.mcpServers| Agent[本地 ACP Agent]
    Agent -->|MCP stdio| Builtin[内置 Rust MCP 子进程]
    Builtin -->|带令牌的本机请求| Router[应用工具路由]
    Router -->|Tauri 请求与响应| UI[画布与提案状态]
    Agent -->|MCP stdio / Streamable HTTP| External[第三方 MCP 服务]
```

### 3.1 内置服务

- 打包一个独立的 Rust 控制台子程序 `agentikz-mcp`，通过标准 stdio 向 Agent 提供 MCP 工具。
- 使用官方 Rust SDK `rmcp`，不自行编写 MCP 握手、错误编码和协议版本协商。
- 子程序只承担协议和转发；画布数据与提案仍由应用管理，避免出现两份文档状态。
- 子程序通过带临时令牌的本机桥接访问应用。建议桥接使用仅监听 `127.0.0.1` 随机端口的 HTTP 请求；它是应用内部通信接口，不对外宣称为 Streamable HTTP MCP。
- 令牌只在当前请求有效，并绑定窗口、聊天、项目和画布；请求结束或取消后失效。
- 单独的控制台程序便于保证 Windows 管道输入输出正常。打包时隐藏进程窗口；日志写 stderr，stdout 只输出协议消息。
- 不增加系统 Node.js 依赖；开发环境和安装包都必须能定位该子程序。

**取舍**：增加原生子程序的构建与打包工作，换取统一的 stdio 兼容路径和明确的进程生命周期。首版不同时建设另一个公开 HTTP MCP 入口。

### 3.2 外部服务

- 由 AgenTikZ 管理配置，ACP Agent 作为运行时 MCP 客户端连接外部服务。
- 在 `initialize` 完成后读取 Agent 能力，再组装 `session/new.mcpServers`。
- 首版支持 stdio 与 Streamable HTTP。HTTP 仅在 Agent 声明支持时传入；不支持时在设置和会话中明确显示未挂载原因，不静默丢弃。
- stdio 的命令路径解析为绝对路径，参数使用数组保存，复用现有可执行文件检测和 Windows 启动经验。
- 首版不提供每个 stdio 服务独立的工作目录配置：ACP 的服务配置没有该字段，不能把一个仅在测试时有效的目录选项当成运行时能力。
- 不修改用户 CLI 的全局配置文件，避免影响其在其他应用中的使用。
- 应用不默认下载第三方服务依赖。缺少运行时或可执行文件时提供诊断。

**边界**：应用可负责独立连通性测试，但测试通过仅表示测试连接成功。运行时由 Agent 建立的是另一条连接，必须区分“测试通过”“已提交到会话”和“本轮已实际调用”。

## 4. 设置页与使用体验

新增独立导航项 **MCP 服务**，避免继续扩充 Agent 配置长页。

### 4.1 内置 AgenTikZ 服务

- “允许 Agent 使用 AgenTikZ 工具”开关，默认开启。
- 展示实际服务状态、工具数量、启动错误和最近一次调用。
- 提供“测试内置工具”，调用只读工具验证完整链路。
- 明确说明：画布修改先生成 Diff 提案，点击应用后才写入画布。

### 4.2 外部服务列表

每行展示：服务名、连接类型、启用开关、适用 Agent、最近测试结果。

操作：添加、编辑、测试、查看工具、删除、导入/导出配置。

服务编辑表单：

| 字段 | stdio | Streamable HTTP |
| --- | --- | --- |
| 名称 | 必填，同一列表唯一 | 必填，同一列表唯一 |
| 启动命令 | 可执行文件路径或可解析命令 | 不适用 |
| 参数 | 独立参数项，可切换 JSON 数组编辑 | 不适用 |
| 环境变量 | 支持普通值与敏感值 | 不适用 |
| 服务地址 | 不适用 | 完整 MCP endpoint |
| 请求头 | 不适用 | 支持普通值与敏感值 |
| 适用 Agent | 全部或指定 Provider | 全部或指定 Provider |

新建/导入的外部服务默认不启用。用户开启后，下一次发送消息时挂载；不要求新建聊天。

“测试”只执行协议协商与工具发现，不主动调用第三方业务工具。连接失败保留可操作的错误原因，如命令不存在、鉴权失败、握手超时、协议不兼容。

导入兼容常见 `{"mcpServers": {...}}` 结构，先预览再保存；无法识别或不支持的字段逐项提示。导出默认排除密钥。

## 5. 内置工具范围

首版工具集中在当前绘图任务，复用现有 TypeScript 实现。

| 工具 | 返回或行为 | 首版处理 |
| --- | --- | --- |
| `get_canvas_source` | 源码、画布标识、版本和主题 | 新增只读工具 |
| `get_canvas_ast` | 节点、连线、图表、源码位置及版本 | 实际调用解析器 |
| `get_selected_elements` | 当前选中元素及对应源码 | 实际读取选区 |
| `inspect_layout_diagnostics` | 问题列表、评分；可检查某个待应用提案 | 复用布局诊断 |
| `get_component_library` | 组件说明和可选参考片段 | 复用组件库 |
| `get_theme_palette` | 当前或指定主题的语义色板 | 复用主题配置 |
| `propose_tikz_patch` | 完整源码提案与 Diff | 进入待应用提案 |
| `propose_surgical_diff` | SEARCH/REPLACE 合并后的提案 | 搜索不唯一或未命中即报错 |
| `propose_layout_repair` | 自动修复生成的提案与诊断结果 | 进入待应用提案 |

现有 `apply_surgical_diff` 与 `auto_repair_layout` 尚未作为服务对外发布，建议现在改成 `propose_*` 命名，准确表达其默认行为。

每个工具都提供真实 schema 和处理器，成功返回结构化结果，业务失败返回可识别的工具错误。只有实际成功的调用才显示完成。

首版不增加任意 shell、通用文件写入、文件删除等内置 MCP 工具；已有 ACP 原生工具负责这些能力。论文编译、导出和资产管理可在绘图链路稳定后扩展。

## 6. 目标绑定与修改一致性

这是首版必须实现的正确性要求。

### 6.1 调用上下文

每轮请求建立不可变的目标绑定：

```text
requestId / conversationId / windowId / projectId / canvasId
```

每次读取再返回当前 `revision` 与 `sourceHash`。生成提案时必须附带基准版本。

- 前端的工具请求监听在应用层统一注册，先完成监听和目标注册，再启动 Agent。
- Rust → 前端请求包含独立 `toolRequestId`；前端通过 Tauri command 返回结果。
- Rust 使用有超时的待响应表关联结果。超时、取消、窗口关闭均移除对应项。
- 只接受来自目标窗口、目标请求的结果，不能用当前活动聊天替代原聊天。

### 6.2 切换画布

首版采用明确的保守行为：用户切换到其他画布后，原请求的后续画布工具返回 `target_inactive`，提示回到原画布继续；不自动切换，也不把调用重定向到新画布。

组件库、固定主题查询等不依赖当前画布的工具仍可执行。

### 6.3 应用提案

提案持有 `targetCanvasId + baseRevision + baseSourceHash`：

- 点击应用时再次核对目标和源码版本。
- 目标不一致或源码已改动时提示重新生成，首版不自动合并冲突。
- 应用走现有 Workspace 修改、撤销和 Project 保存链路。
- 同轮针对同一基准反复优化，更新同一张待应用卡片，并保留 proposalId。
- 工具生成的提案与最终文字回复去重，避免一个修改出现两张可应用卡片。
- 原有文本解析提案同步加入相同的目标/版本校验，避免两条路径行为不同。

## 7. 权限边界

| 能力 | 开启条件 | 与“完整本机访问”的关系 |
| --- | --- | --- |
| 内置画布只读工具 | 开启内置 MCP | 不要求完整本机访问 |
| 内置画布修改提案 | 开启内置 MCP；应用时版本匹配 | 默认仍需点击应用 |
| ACP 文件读写与原生命令 | 现有完整本机访问设置 | 沿用上一轮实现 |
| 外部 MCP 服务 | 用户单独启用该服务 | 服务按其自身权限运行 |

**外部 MCP 直连意味着应用不能承诺对每个工具进行拦截。** 完整本机访问开关不会自动把第三方服务变成只读服务。设置页应说明这一点；首版不提供无法落实的逐工具权限开关。

若后续需要“只允许某几个工具”或“每次写操作确认”，应引入统一 MCP 代理，在实际调用路径实施控制，再开放相应 UI。

本机桥接只接受有效临时令牌和允许的操作；不向外开放监听，不把令牌写进日志和持久化配置。

## 8. 配置、密钥和运行状态

- 新增独立 `useMcpStore` 管理服务列表和状态；`useSettingsStore` 只保存必要开关。
- 后端将配置存入应用数据目录的 `mcp/servers.json`，采用版本化 schema 和原子写入。
- 敏感环境变量和鉴权请求头使用系统凭据存储，配置文件只保存引用；存储不可用时提示使用本次会话临时值，不自动降级为明文保存。
- 配置包含稳定 id、显示名、连接类型、启用状态、适用 Agent、连接参数与配置版本。
- 服务测试结果与运行状态不持久化成“已连接”；重启后重新检测。
- 日志默认记录服务名、工具名、耗时、状态和脱敏错误，不默认保存完整文件内容或密钥。

建议状态：

```text
未启用 → 待测试 → 测试中 → 测试通过 / 测试失败
会话侧：待挂载 → 配置已提交 → 本轮已调用 / 挂载失败
```

ACP 请求目前是短生命周期：先保持每轮建立服务连接、结束清理的模式，避免同时引入长期会话管理改造。

独立测试进程由应用负责清理；运行中的外部 stdio 服务通常由 Agent 启动，应用需验证 Agent 退出后的进程回收行为。不能仅凭关闭测试连接就声称所有子孙进程已结束。

## 9. 协议与兼容策略

- 保持项目现有 ACP v1，使用现有 Rust SDK 的 `mcp_servers(...)` 类型构造，不混入 ACP v2 草案。
- 外部 HTTP 接入按 `initialize` 返回的 MCP transport 能力判断。
- 内置服务选用正式发布的 `rmcp` 版本并锁定依赖，协商兼容现有适配器使用的 MCP 版本。
- 截至本设计日期，官方 Rust SDK 已支持 2026-07-28 规范及此前版本；不能假设当前 Agent 全都支持该规范。首版兼容测试必须覆盖旧版 `initialize` 生命周期。
- 旧 HTTP+SSE、OAuth 自动登录、MCP-over-ACP、公网隧道、服务市场、第三方客户端独立接入不进入首版。
- 未支持的鉴权方式和传输类型直接显示“不支持”，不伪装为网络故障。

## 10. 实施阶段与验收

### 阶段 A：内置服务形成闭环

交付：Rust MCP 子程序、本机桥接、ACP 注入、9 个内置工具、提案绑定与版本校验、真实工具记录。

验收：

1. Agent 通过 MCP 读取实际画布；源码变化可被后续读取观察到。
2. 布局诊断与界面快捷操作对同一源码给出一致结果。
3. MCP 提交修改后出现 Diff，应用前画布不变，应用后可撤销。
4. 切换画布、修改源码、关闭窗口、超时与取消均不会写错图或挂起待响应项。
5. 关闭内置服务后，下一轮不再挂载；当前轮立即使其授权失效并返回明确错误。
6. 开发环境和安装包均可启动子程序，Windows 不弹黑色控制台窗口。

### 阶段 B：外部服务管理

交付：MCP 设置页、stdio/HTTP 表单、适用 Agent、连通测试与工具发现、配置导入导出、凭据存储、运行状态。

验收：

1. 测试用 stdio 服务与 HTTP 服务可被发现并经真实 Agent 调用。
2. 禁用、删除或修改服务在下一轮生效，当前轮显示正在使用旧配置，避免误以为立即断开。
3. 不支持 HTTP 的 Agent 显示明确原因，且不收到不支持的配置。
4. Windows 空格路径、Unicode、参数边界、环境变量与鉴权请求头正确传递。
5. 安装目录、项目文件及 CLI 全局配置不被意外写入。
6. 凭据不出现在普通配置、导出文件、日志或错误提示中。

### 阶段 C：扩展能力（另行审查）

自动应用画布修改、长期 ACP 会话、统一外部工具代理与逐工具授权、论文与资产工具、供第三方应用连接的独立服务入口。

**建议阶段 A、B 完成后作为一个可用功能交付，不把只有设置页或只有工具清单的状态视为完成。**

## 11. 预计涉及的代码位置

以下为拟定边界，实施时可按实际依赖调整：

- `src-tauri/src/mcp/`：配置、状态、本机桥接、请求上下文与工具路由。
- `src-tauri/src/bin/agentikz-mcp.rs`：标准 stdio MCP 入口。
- `src-tauri/src/acp/mod.rs`：能力检测、服务注入、生命周期和事件关联。
- `src-tauri/src/lib.rs`：配置和工具响应 commands。
- `src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`、构建脚本：依赖与子程序打包。
- `src/store/useMcpStore.ts`：服务管理状态。
- `src/core/mcp/`：复用解析/诊断能力的工具处理器与应用级请求监听。
- `src/components/settings/McpSettingsPane.tsx`：服务配置页。
- `src/types/acp.ts`、`src/store/useAgentStore.ts`：真实调用来源、提案目标与版本。
- Workspace / Project Store：画布版本和应用前一致性检查。
- 集成测试：协议、桥接、Agent 挂载、提案冲突、进程清理和安装包。

## 12. 建议审查的决策

1. 是否接受首版同时包含“内置画布服务”和“外部服务管理”。
2. 是否接受内置服务使用打包的 Rust stdio 子程序，本机桥接仅用于与应用交换状态。
3. 是否接受首版画布修改默认生成待审核提案，自动应用放到后续。
4. 是否接受外部服务首版直连、独立启用，暂不提供逐工具权限控制。
5. 是否接受 HTTP/SSE 旧传输、OAuth 自动登录和第三方客户端独立接入延后。
